# REL ICL: TRAINING -FREE RELATIONAL LEARNING WITH TABULAR FOUNDATION MODELS

## ABSTRACT 

Tabular foundation models achieve state-of-the-art performance on single-table tasks without any training. Recent work suggests that they are also well-suited for relational learning via deep feature synthesis (DFS), which flattens a relational schema into a single table by adding aggregates of the other tables’ columns as fea-tures. This approach is appealing because it directly benefits from improvements to or customization of the underlying tabular foundation model. In this paper, we identify two key problems with DFS: feature explosion and interaction blindness .The first problem arises because the number of DFS features grows quickly as the schema becomes more complex, limiting scalability and performance. The second problem arises because column-wise aggregates do not account for feature interactions, limiting performance. We propose and explore an alternative method termed RelICL, which keeps the benefits of DFS but alleviates these two prob-lems. At its heart, RelICL propagates and fuses information step by step through the schema graph, using the same tabular foundation model that is eventually used for prediction to do so. In our experimental study using RelBench tasks, RelICL was on par with the strongest approach based on deep feature synthesis. 

## 1 INTRODUCTION 

Relational data is ubiquitous in industry and science (Fey et al., 2024), spanning application ar-eas like e-commerce, social networks, and clinical research (Robinson et al., 2024). A relational database can be understood as a collection of multiple tables, interconnected with each other via foreign key references (Codd, 1970; Garcia-Molina et al., 2009). In this paper, we explore how to leverage strong tabular foundation models for relational learning. Tabular foundation models (TFMs) such as TabPFN (Hollmann et al., 2022; 2025), TabICL (Qu et al., 2025; 2026), and others (Ma et al., 2025; Zhang et al., 2025; Spinaci et al., 2025; Kong & Das, 2026) are pretrained on a large amount of synthetic and/or real-world tabular data. They reach state-of-the-art performance for single-table learning tasks using in-context learning, i.e., without further training. For example, on the tabular benchmark TabArena (Erickson et al., 2025), most top-ranked models 1 are TFMs, outperforming gradient-boosted trees such as XGBoost (Chen & Guestrin, 2016), deep tabular models such as RealMLP (Holzm¨ uller et al., 2024), and AutoML systems such as AutoGluon (Erickson et al., 2020). A natural and practically important question is whether and how TFMs can be leveraged for re-lational learning on a set of interconnected tables. More specifically, given a task table holding in-context examples and prediction targets, how can we leverage information from the remaining 

context tables ? Deep feature synthesis (DFS) (Kanter & Veeramachaneni, 2015) provides one an-swer to that question: It extends the task table with additional DFS features , each obtained by aggre-gating values from a single context table column, and then applies a TFM to the resulting extended task table . To do so, DFS follows meta-paths (Sun et al., 2011), i.e., chains of foreign key references that start at the task table and end at a context table. For every such meta-path, DFS aggregates the

For example, in a social network task, a DFS feature may hold the average age of the friends of a given user. DFS needs no training, it can be used with any tabular model, including TFMs, and it can reach state-of-the-art results for relation learning (Xu et al., 2026; Hayler et al., 2026). DFS is implemented in several frameworks such as Featuretools (Kanter & Veeramachaneni, 2015), RDBLearn (Xu et al., 2026; Zhang et al., 2026) and TabPFN-Rel (Hayler et al., 2026). Despite its simplicity and strong empirical performance, applying DFS in practice can be challeng-ing due to feature explosion : the number of DFS features grows quickly as the schema becomes more and more complex. Since DFS aggregates every column along every meta-path using multiple aggregation functions, the width of the extended task table grows with the number and width of the context tables, limiting scalability. For this reason, practical DFS approaches need to use strategies such as capping meta-paths length or pruning DFS features (Kanter & Veeramachaneni, 2015; Lam et al., 2017; Xu et al., 2026; Hayler et al., 2026), limiting performance. A second inherent limitation of DFS is interaction blindness : since each DFS feature is an aggregate of a single column, DFS cannot capture interactions between the columns the context tables. Any task that relies on such interactions is therefore impossible to solve with DFS. In this paper, we explore the question of whether we can keep the benefits of DFS, i.e., training-free relational prediction using any tabular foundation model, while avoiding its drawbacks of feature explosion and interaction blindness. To do so, we propose a simple approach termed RelICL. Like DFS, RelICL builds an extended task table fed into a TFM for the final predictions. Unlike DFS, RelICL also exploits the TFM to build the extended task table. In more detail, the TFM is addi-tionally used for feature extraction (row embeddings from the context tables) and feature fusion 

(propagating row embeddings step by step). RelICL does not suffer from feature explosion because the number of additional features only depends on the size of the local neighborhood instead of on the full database. RelICL does not suffer from interaction blindness because it propagates, pools, and fuses row embeddings instead of individual context-table columns. RelICL works out of the box with any TFM which provides row embeddings, e.g., most recent TFMs including TabICL (Qu et al., 2026), TabPFN (Hollmann et al., 2025), or TabFM (Kong & Das, 2026). To summarize, the contributions of this paper are: (C1) We identify two major limitations of DFS, feature explosion and interaction blindness (Sec. 2) and show that there are tasks for which DFS-based predictors can do no better than random guessing. (C2) We propose RelICL (Sec. 3), which avoids both limitations by replacing column-wise aggregation along meta-paths with propagation and fusion of row embeddings along individual foreign key references. (C3) We report on an ex-perimental study (Sec. 4) using the 21 entity tasks of RelBench (Robinson et al., 2024; Gu et al., 2026), indicating that RelICL is on par with the strongest DFS-based approach (and outperforming many alternative approaches) and that the underlying TFM can be easily swapped. Source code and results are available at https://github.com/uma-pi1/relicl .

## 2 DEEP FEATURE SYNTHESIS AND ITS LIMITATIONS 

2.1 PRELIMINARIES 

A relational database D is a set of tables interconnected by references, see the example in Fig. 1a. We follow Fey et al. (2024); Robinson et al. (2024) and model relational learning via a task table 

T , which holds in-context examples ( Ttrain , green in Fig. 1a) and query rows (Teval , yellow), and multiple context tables , which hold auxiliary information. A reference links the rows of two tables via key columns: if two rows have the same key value, they are linked together. For example, in Fig. 1a, there is a reference between lap times (key r id ) and results (key r id ). References can be one-to-one, many-to-one (e.g., lap times and results ) or many-to-many (e.g., task and results ). Tables and references can be represented via a schema graph .

Problem statement. Given D, Ttrain , and Teval , use a pretrained tabular foundation model T to predict the target attribute of the rows in Teval .A related task is relational deep learning (Fey et al., 2024; Robinson et al., 2024), which adds a temporal component for tasks such as forecasting. Here predictions at time t must not be influenced by data newer than t. For example, to predict whether Cathi wins the next race in the example of Fig. 1a, we should not already be aware of the results of the next race. We follow Fey et al. 2Preprint. (2024); Robinson et al. (2024) and address such tasks by temporal filtering using a cut-off time (gray “future” rows in Fig. 1a) and temporal pooling (discussed later). In most of the following discussion, we ignore the temporal component for ease of exposition. Our problem statement specifically requires the use of a single TFM. Approaches such as graph neural networks (Fey et al., 2024; Robinson et al., 2024; Chen et al., 2025; Dwivedi et al., 2025), which are trained per database, and relational foundation models (Ranjan et al., 2025; Kothapalli et al., 2026), which are pretrained on a relational database corpus, fall outside this setting. We focus on TFMs because they achieve state-of-the-art single-table performance, large corpora of tabular data are readily available (Gardner et al., 2024), TFMs are actively developed and continuously improved, and TFMs are easy to customize for a particular domain via continual pre-training. Any advances in TFMs thus directly translate to advances in relational learning based on TFMs. 2.2 DEEP FEATURE SYNTHESIS 

Deep feature synthesis (Kanter & Veeramachaneni, 2015) extends the task table T by DFS features, i.e., columns derived from the context tables along meta-paths, and uses the resulting extended task table TDFS for prediction. A meta-path P = ( T, R 1, . . . , R L) of length L is a sequence of L+1 tables starting at the task table T such that every two consecutive tables are connected by a reference. For example, ( task , results , lap times ) is a length-2 meta-path in Fig. 1a. Given a meta-path, DFS determines for every row x in T the set of rows P (x) in RL that are reachable from r by following the meta-path P .2 The columns in P (x) are then aggregated individually using multiple aggregation functions, e.g., length, mean/min/max/std (for numerical columns), mode/value frequencies (for categorical columns). The resulting aggregates then form the DFS features for meta-path P . This process is repeated for each meta-path. The number of meta paths is at least linear but can be exponential with respect to the number of tables in the database (Lam et al., 2017). Once the extended task table has been obtained, any tabular model can be used for prediction. This includes classical models such as XGBoost (Chen & Guestrin, 2016), CatBoost (Prokhorenkova et al., 2018), or LightGBM (Ke et al., 2017), deep tabular models such as RealMLP (Holzm¨ uller et al., 2024) or FT-Transformer (Gorishniy et al., 2021), and tabular foundation models as in the recent approaches RDBLearn (Xu et al., 2026; Zhang et al., 2026) and TabPFN-Rel (Hayler et al., 2026). 2.3 FEATURE EXPLOSION 

Limitation 1 (Feature explosion) . The number of DFS features grows with the complexity of the schema. The extended task table holds one column per combination of (i) meta-path, (ii) column of the context table where that meta-path ends, and (iii) aggregation function. Its width is therefore 

O( #meta-paths ⋅ #attributes ⋅ #aggregates ). For instance, the RelBench database rel-f1 (Robin-son et al., 2024) holds nine tables with 67 columns in total (App. D.1). RDBLearn generates 7 715 columns on the driver-top3 task with its six default aggregation functions (before pruning down to 5 460, unbounded depth), more than one hundred times the width of the schema itself. In practice, this problem needs to be addressed. Some works do this by selecting a small set of meta-paths manually (Wang et al., 2019), whereas others aim to learn promising meta-paths (Ferrini et al., 2024). The perhaps most common approach, however, is to bounds the maximum length of the considered meta-path, the depth (Kanter & Veeramachaneni, 2015; Xu et al., 2026; Hayler et al., 2026). In fact, the latest versions of featuretools (1.31.0) (Kanter & Veeramachaneni, 2015), RDBLearn (1.1) (Xu et al., 2026), and TabPFN-Rel (Hayler et al., 2026) all use a maximum depth of 2 by default. Such an approach can be highly problematic, however. 

Prop. 1 (Insufficiency of bounded depth) . For every depth bound D, there are relational prediction tasks that no DFS-based approach can solve better than random guessing. 

This problem arises when the relevant signal for prediction is too far away from the task table, and it holds no matter how powerful the tabular model or the considered aggregation functions are. As a

These methods milden the problem, but they also require computation of all DFS features first and they ultimately may remove relevant information from the extended task table. 2.4 INTERACTION BLINDNESS 

Limitation 2 (Interaction blindness) . DFS-based methods are oblivious to feature interactions. Since each DFS feature is an aggregate of a single context-table column, DFS-based approaches are inherently oblivious to feature interactions. In fact, Xu et al. (2026) makes single-column aggrega-tion their “guiding principle” according to which aggregates should compress only within but not across columns. Again, such an approach can be highly problematic. 

Prop. 2 (Insufficiency of DFS features) . There are relational prediction tasks that no DFS-based predictor can solve better than random guessing. 

This arises when the signal required to solve the task lies solely in feature interactions, but not feature values. Consider, for example, a relational learning task with one context table, in which every task table row references exactly three rows in the context table The three rows are either 

{( 0, −1), (1, 0), (2, 1)} (positive correlation) or {( 0, 1), (1, 0), (2, −1)} (negative correlation), and the task is to predict which of the two cases hold. Since each column has the same set of values, all DFS features necessarily coincide for both cases so that a DFS-based method cannot distinguish between them. Tab. 2 validates this empirically (1000 training rows, 300 query rows, 3 seeds): RDBLearn (v1.1, default configuration) is no better than random guessing, whereas RelICL (Sec. 3) has good performance. App. B.2 provides further details. One way to combat interaction blindness is to engineer additional features, e.g., manually or via an LLM (App. A). Such an approach is challenging to get right, however, and may lead to further feature explosion. 

## 3 REL ICL 

We now describe RelICL, which avoids the drawbacks of feature explosion and interaction blind-ness. At its heart, RelICL is a very simple approach; see Fig. 1. Its key idea is to use a TFM for both final predictions (as in DFS) but also for feature extraction and feature fusion (unlike DFS). More specifically, RelICL represents context-table rows via row embeddings extracted by the TFM. It fuses information from a referenced context table by adding pooled row embeddings as additional features. We first discuss the assumptions underlying RelICL, and then describe the approach in more detail. 3.1 ROW EMBEDDINGS ARE GOOD FEATURES 

We consider TFMs T based on row embeddings. To obtain predictions for a table R, T first uses an encoder Tenc to extract row embeddings of the training and query rows 3 (without the target attribute) and subsequently applies a prediction head Tpred (using the target attribute of the train rows). In short, T ( R) = T pred (T enc (R)) . Most most recent TFMs, including TabICL (Qu et al., 2026), TabPFN (Hollmann et al., 2025), TabDPT (Ma et al., 2025), LimiX (Zhang et al., 2025), and TabFM (Kong & Das, 2026), follow this approach.

This in turn simplifies RelICL’s feature fusion: use (pooled) row embeddings from context tables as additional features. Intuitively, this assumption appears reasonable: since Tpred only relies on Tenc (R) (but not on R itself), the row embeddings must summarize the corresponding rows of R adequately for 

T to work well. We tested this assumption on ten single-table binary classification datasets from OpenML (Van-schoren et al., 2014). For each task, we compared TabICL on the original table ( T ( R)) against TabICL on the row embeddings ( T (T enc (R)) ). App. C.2 provides dataset statistics and further details, Tab. 3 shows the results. We found that for most datasets (all except philippine and jas-mine), there was no statistically significant loss in performance, providing some justification for our assumption. 3.2 FEATURE EXTRACTION AND FEATURE FUSION 

RelICL operates in three phases: 1. Outward traversal to determine relevant context table rows 2. Inward traversal to extract and fuse features from context tables 3. Prediction on the extended task table The first two phases rely on a partial ordering of the tables in the database, which we represent as an inference DAG (see Fig. 1b) with root T (the task table). An edge R → S in the inference DAG states that (i) there is a reference between table R and table S and (ii) the rows of R should be fused into the rows of S. To obtain the inference DAG, RelICL uses breadth-first search starting at the task table so that tables more distant to the task table are fused into tables closer to the task table. 

Outward traversal. Not every row in every context table is relevant in that it is directly or indirectly referenced by a row in the task table. Irrelevant rows do not need to be propagated, and the goal of the outward traversal is to determine and prune such rows. In Fig. 1a, for instance, there is no prediction task for driver 3 so that the results of driver 3 are irrelevant. Pruning irrelevant rows is especially beneficial due to the asymptotically quadratic cost of attention (Vaswani et al., 2017) with respect to the number of rows in typical tabular TFMs (Qu et al., 2026; Hollmann et al., 2025). During outward traversal, we traverse the inference DAG in reverse topological order, starting at the task table. When processing a table, we first determine its set of relevant rows (all for the task table) 6Preprint. and then propagate the corresponding set of relevant keys along every reversed edge (e.g., {1, 2}

from task →results or {11 −14 , 15 , 16 , . . . } from results →lap times ). All rows that do not contain a relevant key are marked irrelevant and dropped (e.g., row 19 in results ). 

Inward traversal. The goal of inward traversal is to propagate information from the context tables towards the task table, ultimately constructing the extended task table. This time, the inference DAG is processed in topological order. Whenever a table R is processed, we fuse information from its children (along incoming edges) into the table to obtain R+, extract and pool row embeddings of 

R+, and finally propagate information to the parents (along outgoing edges). Each row r+ of R+

is meant to represent (i) the corresponding row r from R and (ii) all the rows from all descendant tables referenced by r.

Feature extraction. The extraction of features for some table R+ makes use of Asm. 1: we run the encoder Tenc on R+ to obtain a row embedding for every row of R+ (cf. Fig. 1c). In contrast to using the rows directly, this has the advantage that (i) the size of the row embeddings is independent of the width of the table and (ii) each element of each row embedding depends on the entire row (and not just one column). The first advantage allows us to avoid feature explosion: adding features to R to obtain R+ does not affect the size of the information propagated towards R’s parents. The second advantage avoids interaction blindness. 

Feature fusion. We now describe how to fuse information from R’s children into R to obtain R+.Consider a child C → R in the inference DAG. Since tables are processed in topological order, C has already been processed when processing R, so that an embedding for every row of C+ is available. We now extend R by a block of columns holding pooled row embeddings. In more detail, for every row r in R, we pool the row embeddings of the rows in C that are referenced 4 by r (e.g., row 11 of 

results references the first two rows of lap times ), e.g., using sum, average, or max pooling. Since the latter two methods are oblivious to the number of referenced rows, we also add an explicit count column with that number in the spirit of the degree scalers of Corso et al. (2020). These numbers are shown in parentheses in Fig. 1c. 

Prediction. The inward traversal stops after processing the task table T to obtain the extended task table T +. The number of features in T + is determined by the number of its children in the inference DAG (one in Fig. 1), not the number of tables in the entire database. RelICL does not need (nor does it use) a depth bound to avoid feature explosion. A row t+ ∈ T + thus summarizes all the rows referenced from the corresponding row t ∈ T , no matter how far away. To obtain the final prediction, RelICL runs the entire tabular model on the extended task table, i.e., T ( T +).

## 4 EXPERIMENTS 

We performed an experimental study on RelBench in which we compared RelICL to the state-of-the-art DFS-based approaches and other methods pretrained on relational data. We found that RelICL (in its default configuration) was on par with the strongest DFS-based approaches and outperformed the pretrained relational approaches. We also provide evidence that the underlying TFM used by RelICL can be easily swapped. Our complete source code and experimental results are available at

RelICL implementation. RelICL uses a number of implementation tricks to speed up processing. Finally, it merges the tables of some many-to-one relationships, which roughly corresponds to propagating rows instead of row embeddings when no pooling is needed. App. C.1 contains more details.

The same ensemble members are used for all classification and regression tasks, respectively. More details are given in App. D.4. RelICL has 11 hyperparameters (such as sample sizes or the amount of dimensionality reduction). The global hyperparameter settings have been selected via random search over 100 trials per task, optimizing for overall validation AUROC (classification) and MAE (regression) on a subset of 6 classification and 6 regression tasks from RelBench. The ensemble members differ in hyperparam-eters that are highly-sensitive according to this search. App. D.3 has further details.

## 5 CONCLUSION 

Feature explosion and interaction blindness are two inherent limitations of deep feature synthesis for relational learning with tabular foundation models. We explored whether these limitations can be avoided while keeping its benefits. We proposed RelICL, a simple training-free approach that uses a tabular foundation model for multiple purposes (feature extraction, feature fusion, and final predic-tion). RelICL does not suffer from the limitations of DFS and had strong empirical performance in our experimental study. 10 Preprint.

## A EXTENDED RELATED WORK 

This appendix covers further related work which is not directly relevant to follow the paper. 

Graph-based approaches. Rather than first flattening the schema and then running inference, graph-based approaches work on the schema directly to make predictions end-to-end. Schlichtkrull et al. (2018); Cvitkovic (2020); ˇ S´ ır (2021) were among the first to frame supervised learning over relational databases as a graph neural network (Scarselli et al., 2008) problem, with one node per row and one edge per foreign key. Fey et al. (2024) later formalize and coin this idea as Relational Deep Learning (RDL). RDL puts a particular focus on the time domain and hence builds upon tem-poral graph learning (Rossi et al., 2020). In its basic form, a heterogeneous graph neural network such as GraphSAGE (Hamilton et al., 2017) or ID-GNN (You et al., 2021) is trained from scratch for every database and task (Robinson et al., 2024). Work since then follows three lines. The first improves message passing itself. RelGNN (Chen et al., 2025) passes messages across many-to-many relationships in a single hop and thereby needs fewer message-passing layers. The second adapts Graph Transformers (Dwivedi & Bresson, 2021) to the relational domain. The Relational Graph Transformer (Dwivedi et al., 2025) tokenizes a node by its type, hop distance, time, and local structure besides its features, i.e., by properties intrinsic to relational data. The third pretrains one relational foundation model across databases and applies it to any database or task, with or without fine-tuning, with the Relational Transformer (Ranjan et al., 2025), PluRel (Kothapalli et al., 2026), Griffin (Wang et al., 2025), and KumoRFM (Fey et al., 2025; Hudovernik et al., 2026) as examples. These models attain strong performance on relational benchmarks, but they need training on rela-tional data, whereas in-context relational prediction asks what a model reaches without any. Among graph-based approaches, Zahradn´ ık et al. (2023); Peleˇ ska & ˇ s´ ır (2025) come closest to our work. They pass messages over the relational schema with a tabular transformer, but train it end-to-end per database, whereas RelICL reuses a frozen backbone without any training. 

Relational benchmarks. Benchmarks for relational data have moved from plain collections of databases to standardized prediction tasks. The CTU Prague Relational Learning Repository (Motl & Schulte, 2025) is the largest such collection, with almost 150 SQL databases. It proposes a target column for many of them, but no splits or evaluation protocol. RelBench (Robinson et al., 2024; Gu et al., 2026) adds both and pairs seven databases with 30 tasks. Each task is an SQL query evaluated at a cutoff time, so a model only sees data that existed at prediction time. Wang et al. (2024) release 4DBInfer at the same time. It varies four dimensions: dataset, task, graph extraction, and base predictor. We evaluate on RelBench since all baselines we compare against report on it. Further benchmarks aim to consolidate several approaches into one. ReDeLEx (Peleˇ ska & ˇ S´ ır, 2026) serves over 70 CTU databases through the RelBench interface, so their targets become RelBench-style tasks. Those tasks may be static, whereas RelBench tasks are always temporal. RelBench v2 (Gu et al., 2026) grows to 11 databases and adds the 4DBInfer tasks. It also introduces autocomplete tasks, which predict missing values inside a table. RelArena (Hayler et al., 2026) defines an evaluation protocol on RelBench. It follows TabArena (Erickson et al., 2025) from the tabular domain.

Data. The database holds the task table and a signals table (Fig. 3). Training and test entities are disjoint, both splits are balanced, and we used 1 000 training and 300 test entities. We ran three seeds for each method, each of which set the random draws of the data generator and of the model. 

Setup and results. We ran RDBLearn at its default configuration. Deep feature synthesis generated nine aggregates over the signals table: the row count, together with the minimum, maximum, mean, and standard deviation of each of the two columns. Each of them takes a single distinct value across all training entities, so the feature generator inside RDBLearn’s preprocessor discarded all nine and the base estimator received only the join key. RDBLearn therefore can only randomly guess labels. 

## C METHOD DETAILS 

C.1 SCHEMA REWRITES 

A schema rewrite is a view on the database that removes tables before fusion (Sec. 3.2). Every remaining table costs one forward pass of the tabular model. The views read the temporally filtered tables, so RelICL applies the rewrites once, and each timestamp only changes the filter. 

Inlining. RelICL left-joins leaf tables into every table that references it and then drops it, which adds columns but no rows. In an entity task in RelBench, every task row references one entity table 

that describes the entity the prediction is about. RelICL inlines that table into the task table and rewires its remaining references to the task table. 

Junction tables. A junction table R references two tables C1 and C2 and is referenced by none. RelICL replaces R by two copies (Fig. 4). The copy R1 carries the columns of C2 inline and references C1. The copy R2 carries the columns of C1 inline and references C2. Pooling R1 into C1

then passes the attributes of C2 to C1 in one step instead of two, and likewise for R2. This follows RelGNN (Chen et al., 2025), which also passes messages between the two neighbors of a junction table in a single step. C.2 ASM . 1: R OW EMBEDDINGS ARE GOOD FEATURES

D.3 HYPERPARAMETER OPTIMIZATION 

We ran a simple hyperparameter optimization (HPO) scheme to determine a good hyperparameter configuration for the tasks in RelBench. 

Tasks. The search ran independently on six classification and six regression tasks of the 21 Rel-Bench entity tasks (see Tab. 14). The other 9 of the 21 tasks were not used to find a suitable default setting. 

Search space. Tab. 15 lists all 11 hyperparameters, their search space, and the value selected for the configuration RelICL reports throughout the paper, unless declared otherwise. 

Selection. We chose each hyperparameter on its own rather than taking the best single trial. Within each task, we ranked the trials by validation score, since raw scores are not comparable across tasks (Demˇ sar, 2006; Bardenet et al., 2013). For each value of a hyperparameter, we averaged these ranks over all trials and tasks that used this value. This averages over the other hyperparameters, similar to the marginals of Hutter et al. (2014). We then kept the value with the best mean rank (last column in Tab. 15). 

Regression specifics. The target transform was the one exception kept per task type: it is undefined for classification, so it was fixed to none there. 

Run time. Across the 12 studies, the search consumed 121 GPU-hours in total (1200 completed trials), with a mean trial duration of 361 s (median 303 s). Per-task mean trial duration ranged from 55 s ( rel-avito/ad-ctr ) to 887 s ( rel-hm/item-sales ). D.4 CONFIGURATION ENSEMBLING
